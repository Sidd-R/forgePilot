3. Architecture on TrueForge

│ Inline edit (Ctrl+Alt+K) · Agent panel    │ ── turns ──▶    │ agent loop · sub-agents · approvals       │──▶ model
│ Context engine · Review UI · Undo         │ ◀── events ──   │ compaction · deferred tools · routing     │   (any provider
│ MCP server  127.0.0.1 + bearer token      │ ◀─ MCP calls ─  │ (calls our editor tools)                  │    configured in
└───────────────────────────────────────────┘                 └───────────────────────────────────────────┘    TrueForge)

How the extension talks to TrueForge

  • Plain REST + SSE from src/trueforge/client.ts. The TypeScript SDK doesn't load under VS Code's CommonJS resolver.
  • POST /sessions creates a session from an agent spec. A streamed POST /sessions/{id}/turns sends each prompt.
  • If the stream drops, the client resubscribes with /turns/{id}/subscribe?after_event_id=…, so no events are lost.
  • When the agent wants to edit or run a command, TrueForge pauses with tool.approval_required. The extension shows a review and replies with a user.tool_approval event (allow, or deny with a reason).
  • The extension never calls a model provider directly; only TrueForge does. The panel header links to the live TrueForge session (turns and tool calls).

Editor capabilities exposed as MCP tools

  • A local MCP server (Streamable HTTP) binds only to 127.0.0.1 and needs a random per-session bearer token. It is registered with PUT /settings/mcp-servers.
  • forge-editor (preloaded): read_file (up to 400 lines per call), search_code (BM25 search with a token budget), find_text (regex or glob search), propose_edit (multi-file edits), run_command (runs tests; returns the output tail, with a timeout).
  • forge-workspace (deferred tool loading, preload: false): get_diagnostics, git_diff, list_symbols. These load only when the agent asks for them, which keeps the tool list in every prompt small.
  • A path jail keeps every tool inside the workspace. propose_edit is the only way the agent can write to disk.

Harness features used, and why

  • Tool approvals for propose_edit and run_command. A pause becomes an in-editor diff review, so TrueForge's approval drives the review and nothing is saved without the user's consent.
  • Context engineering: dynamic sub-agents (agent mode). Exploration is handed off, and only paths, line ranges and reasons come back, which keeps the main context small.
  • Context engineering: deferred tool loading for the secondary forge-workspace server (see above).
  • Context engineering: compaction at 60k input tokens, so long multi-file runs keep going.
  • Sub-agents and deferred tool loading are visible in the Task B TrueForge session alongside the turns and tool calls. Compaction is a safety net for long runs; it triggers only past 60k input tokens, so a short run like Task B may not reach it.
  • Iteration limits: 60 for the coder agent, 6 for the inline agent.
  • Per-agent tool scoping: enable_tools: [propose_edit] for the inline agent.
  • Deterministic edits: temperature 0 and parallel_tool_calls: false.
  • Turned off: web search, sandbox and generative UI, because the editor doesn't need them.
  • Agent definitions live in agents/*.yaml and are synced to TrueForge with one command (ForgePilot: Load Agent Definitions).

Streaming and cancellation

  • Tokens appear as TrueForge's model.message.delta events arrive over SSE, in both the panel and inline edit. Everything runs asynchronously, so the editor never blocks.
  • Stop (panel button, status bar, or Ctrl+Alt+Backspace) cancels at once. It cancels the TrueForge session, stops retries, backoff and fallback, closes every open review as rejected, and kills any running command.
  • No half-applied edits: files are written only after review, and only if the file hasn't changed since the proposal was built. A cancelled run leaves git status clean.

4. How context is selected

Indexing

  • Files are split into chunks at function, class and heading boundaries (Python, TS/JS, Markdown, RST); other files use line windows. Decorators stay with their function, and Python classes over 40 lines become a header chunk plus one Class.method chunk per method, so a 1,000-line class never fills the budget or hides its methods from search.
  • Each chunk stores its symbol, signature, docstring and token estimate (4 characters ≈ 1 token).
  • Chunks are indexed in MiniSearch BM25, with camelCase and snake_case split into words and name and signature fields boosted 3×.
  • Also built: a symbol table, a repo map (file → top-level symbols), and a co-change map from the last 500 commits of git log.
  • The index is rebuilt on every save. Large (>300 KB), hidden and vendored files are skipped.

Ranking (scores add up per chunk)

  • Lexical: the BM25 score of the request's specific words (top 80 hits). Words found in over 40% of files (for Flask: "flask") are dropped as noise.
  • Exact matches: +10 if the request names a symbol, +5 if it names a file.
  • Editor locality: +4 for the active file, +2 for open tabs and recently edited files.
  • Neighbours of the top 5 files (files ranked by their best chunk): a test or doc partner inherits half its source file's score (for example cli.py → tests/test_cli.py, docs/cli.rst); +1.5 for files changed together in 2+ commits. Data files (.json, .toml, …) are never partners or filename matches.

Budget and packing

  • The default budget is 8,000 tokens (setting: forgepilot.context.tokenBudget).
  • @file and @symbol mentions go in first, capped at half the budget.
  • Next, the top 12 files above a relevance floor (15% of the best score) are chosen. Each gets its best chunk first, in rank order, then up to 3 chunks per file. A chunk is capped at 1,200 tokens with a read_file pointer to the rest. Full text is used until 60% of the budget is spent, then only signatures and docstrings.
  • A repo outline (up to 30 files with their symbols) is added last, if it fits.
  • Every pick carries a reason, merged into one line per file (for example "matched commands, cli, help · test partner of cli.py · 357t"). The panel shows these on a Context picked card, ranked top-down, and they are saved with the chat. This is visible during Task B.
  • For anything else, the agent pulls more on demand with search_code (2,000-token default), read_file or a sub-agent.

Strategy per task: inline edit, agent mode, resilience

① Inline edit (Ctrl+Alt+K)
  • Context: the selection plus about 40 read-only lines on each side. No retrieval, to keep it fast and focused.
  • Agent: the lean forgepilot-inline agent. Its only tool is propose_edit, with at most 6 iterations.
  • Edit format: one small old_text/new_text edit per changed spot, quoted exactly from the selection.
  • Fallback for weak tool-callers: if the model makes no tool call, its fenced code block replaces the selection. The edit is discarded if the selection changed in the meantime.
  • Review: green and red diff in the editor with Accept or Reject CodeLens per hunk. One proposal per turn.
  • Self-repair: afterwards, diagnostics are compared with how the file was before. Up to 2 repair turns fix only errors the edit introduced.
② Agent mode (side panel)
  • Context: an automatic context pack (§4) is sent at the start of the prompt. @file and @symbol mentions are pinned.
  • Agent: forgepilot-coder with all 8 tools, sub-agents and up to 60 iterations. Follow-up prompts continue the same session.
  • Loop: read before assuming, find more with search_code and find_text, then propose edits. It ends with a summary of files changed and why each was chosen.
  • Batched review: a single propose_edit covers every file. Each file opens in its own tab, and one approval answers once every hunk has been decided.
  • Feedback: rejected hunks go back as a deny reason ("do not resend unchanged").
  • Verify: get_diagnostics after edits, then tests with run_command. The user allows a command once or for the whole session.
  • Safety: edits are applied only if the approval matches the reviewed proposal (SHA-256 of its arguments) and the file hasn't changed since. Undo last and Undo run work from checkpoints.
③ Resilience (src/trueforge/resilience.ts, used by both flows)
  • Model chain: each turn tries [primary, …fallbacks] in order.
  • Retry the same model on errors that may clear on their own: 429, 5xx, 408, timeouts, "overloaded", or a dropped stream. It waits 1s, then 3s.
  • Skip to the next model at once on errors that won't go away: 401/403, invalid key, unknown model, refused connection.
  • Silence watchdog: 120s with no stream events counts as a timeout. It is turned off while a turn is paused for review, so a user who takes their time is never treated as a failure.
  • Each attempt starts a fresh session, so a broken session is never reused. The user sees a notice ("Primary model failed… Continuing with X").
  • No partial writes: files change only after review, so a failed attempt never leaves half an edit. If every model fails, the user gets a clear error and git status is clean.

5. Model setup

  • Models: muse-spark-1.3-contributor (primary) and muse-spark-1.3 (fallback), Meta's Muse models.
  • Where they ran: Meta's hosted Muse API (OpenAI-compatible), registered in TrueForge (local mode, on our laptops) as the custom provider muse under Settings → Models. Requests go extension → local TrueForge → model API; the extension holds no keys.
  • Approximate cost: [≈ $X for ≈ N tokens across development and demo]. Cost = (input tokens × input price + output tokens × output price) ÷ 1M, using token counts from TrueForge session usage.
  • Any model works: models are configured only in TrueForge, and ForgePilot refers to them by name. Any catalog provider, AI gateway or local OpenAI-compatible model works with no code change. An example configuration ships in models.example.yaml.
  • Switching models:
    • Add the model in TrueForge (Settings → Models).
    • Set forgepilot.models.primary and the ordered list forgepilot.models.fallbacks in VS Code settings.
    • Run ForgePilot: Load Agent Definitions. Both agents are updated in TrueForge.

8. Known limitations and what we would do with another month

LimitationWhat it means in practiceWhat we'd do with another month
Search matches words, not meaningIf you ask about "login" but the code says "authenticate", the right file may not be found automatically.Add meaning-based (embedding) search alongside word search.
Simple code splittingCode is cut into pieces with pattern rules that only fully understand Python, TS/JS and docs. Token counts are estimates.Use a real parser (tree-sitter) for every language and an exact token counter.
Slow on very large reposThe whole project is re-indexed on every save, and only one workspace folder is supported.Re-index only changed files, and support multi-folder workspaces.
Commands aren't isolatedCommands only run after you approve them, but then they run on your machine with full access.Run them in a sandbox or container, with a list of allowed commands.
Setup and cost visibilityTrueForge needs a special startup flag, and you can't see how many tokens or how much money a run used.One-click setup and a token and cost readout per run in the panel.
